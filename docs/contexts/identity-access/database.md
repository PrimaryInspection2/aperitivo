# Identity & Access — Database Schema

Physical schema for the IAM Bounded Context: tables, columns, constraints, indexes, and migration notes. Derived directly from the [domain model](domain-model.md). Tables: `users`, `user_identities`, `connected_sources`, and `refresh_tokens` (our own refresh tokens, [ADR 0013](../../adr/0013-access-and-refresh-tokens.md)).

Conventions: snake_case identifiers; UUID primary keys; `timestamptz` for all instants (stored UTC); migrations are Flyway per-BC changesets applied at startup.

## Schema ownership

IAM owns its own logical schema within the shared PostgreSQL instance. Other BCs never read these tables directly — they go through IAM's published interfaces or events (see [ADR 0005](../../adr/0005-bounded-contexts.md)). Concretely this is the `iam` schema (or table prefix, depending on the migration tool's layout); the DDL below omits the schema qualifier for readability.

## Tables

### users

```sql
CREATE TABLE users (
    id            UUID        PRIMARY KEY,
    display_name  TEXT        NOT NULL,
    email         TEXT        NULL,
    avatar_url    TEXT        NULL,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

Notes:
- `id` is our internal UUID, generated by the application (not a DB sequence), so it is known before insert and usable as the JWT `sub` and as the FK target everywhere.
- No provider-specific columns by design — see invariant 1 in the domain model. In particular there is **no `google_sub` column**: a sign-in method is a row in `user_identities`, because a user may have more than one.
- `email` is the account's **single contact address**, seeded from the identity provider at signup. Its one consumer is the Notifications BC, which needs somewhere to deliver "your Strava connection broke" mail — reached through IAM's `UserContactReader` published port, never by querying this table. It is **not** an identifier: Google warns against using email as a linking key, Apple may return a per-team private relay address, and Facebook omits the field entirely when no valid address is available (quotes and sources in [ADR 0011](../../adr/0011-identity-provider-signup.md)). Nothing in the system may key off `users.email`.
- **This is the only place the address is stored.** It is not carried on event payloads — Modulith serializes those into `event_publication`, which would copy the address durably into the outbox of every producing module — and it is not projected into the Notifications schema. Erasure therefore touches one row. See [domain-model.md](domain-model.md) for the port rationale.
- `email` and `avatar_url` are **nullable and stay nullable** — a provider may release neither. Notifications must treat a null address as a normal state and fall back to the in-app channel, not as an error.
- No `status` column. A user's existence is binary; connection health lives on `connected_sources`.

### user_identities

How a user signs in. One row per sign-in method.

```sql
CREATE TABLE user_identities (
    id                UUID        PRIMARY KEY,
    user_id           UUID        NOT NULL,
    provider          TEXT        NOT NULL,    -- enum as string: 'GOOGLE', …
    provider_user_id  TEXT        NOT NULL,    -- the provider's `sub` claim, never the email
    created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    last_login_at     TIMESTAMPTZ NULL,

    CONSTRAINT fk_user_identities_user
        FOREIGN KEY (user_id) REFERENCES users (id)
);
```

Notes:
- **No token columns.** An identity provider authenticates the user and is then finished; we mint our own JWT and never call Google on the user's behalf again. Storing OIDC tokens would create a second secret-bearing table with no consumer. Contrast `connected_sources`, whose entire purpose is to keep calling the provider later.
- **No `email` column.** The provider's email claim is written to `users.email`, which is the account's single contact address (see above). A per-identity copy would have **no reader** — email is never a join key by decision, so nothing may query it — and in MVP it would be identical to `users.email` by construction, since there is one identity provider. The only effect would be doubling the personal data that account erasure has to reach. If a second provider ever makes "which provider asserted which address" a question worth answering, it comes back as an additive nullable column; that is a cheap change and an unnecessary one today.
- **No `status` column.** A sign-in method is present or absent; it has no `ACTIVE`/`REVOKED`/`ERROR` lifecycle to track, because nothing background-syncs through it. Removal is a `DELETE`, guarded by "a user must keep at least one sign-in method".
- `provider_user_id` is the provider's stable subject identifier (`sub`), **never** the email address.
- `STRAVA` never appears in this table. Strava is not a sign-in method ([ADR 0011](../../adr/0011-identity-provider-signup.md)).

The row therefore holds exactly what a sign-in method *is*: which provider, which subject, and when it was last used. Everything about the *person* lives on `users`.


### connected_sources

Where a data source lives, and the credentials to keep calling it. Created by the connect flow, **never by login**.

```sql
CREATE TABLE connected_sources (
    id                       UUID        PRIMARY KEY,
    user_id                  UUID        NOT NULL,
    provider                 TEXT        NOT NULL,          -- enum as string: 'STRAVA', …
    provider_user_id         TEXT        NOT NULL,          -- e.g. strava_athlete_id
    access_token             BYTEA       NOT NULL,          -- AES-GCM ciphertext (nonce||ct||tag)
    refresh_token            BYTEA       NOT NULL,          -- AES-GCM ciphertext
    access_token_expires_at  TIMESTAMPTZ NOT NULL,
    refresh_token_expires_at TIMESTAMPTZ NULL,
    scopes                   TEXT[]      NOT NULL DEFAULT '{}',
    status                   TEXT        NOT NULL,          -- 'ACTIVE' | 'REVOKED' | 'ERROR'
    failure_count            INT         NOT NULL DEFAULT 0,
    last_error               TEXT        NULL,
    last_refreshed_at        TIMESTAMPTZ NULL,
    last_used_at             TIMESTAMPTZ NULL,
    version                  BIGINT      NOT NULL DEFAULT 0,  -- @Version optimistic lock
    created_at               TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at               TIMESTAMPTZ NOT NULL DEFAULT now(),

    CONSTRAINT fk_connected_sources_user
        FOREIGN KEY (user_id) REFERENCES users (id)
);
```

Notes:
- `user_id` is a **plain FK column**, not a JPA association — navigation is via repository methods (see the persistence policy in the domain model). The DB-level `FOREIGN KEY` still enforces referential integrity; that is independent of how the ORM maps it.
- `access_token` / `refresh_token` are `BYTEA`: the application encrypts with AES-GCM via `EncryptedBytesConverter`, storing `nonce || ciphertext || authTag`. The DB never sees plaintext.
- `provider` and `status` are stored as `TEXT` (matching `@Enumerated(EnumType.STRING)`), not native PG enums — easier to evolve (adding `GARMIN` is an application enum change, no `ALTER TYPE`).
- `scopes` is a native Postgres `TEXT[]`, mapped by the custom array type. Small fixed set; never queried element-wise, so an array beats a join table here.
- `version` backs Hibernate `@Version` optimistic locking, used to serialize concurrent token refreshes.

### refresh_tokens

Our own refresh tokens — one row per issued token. Introduced by [ADR 0013](../../adr/0013-access-and-refresh-tokens.md). Written by login (a new family) and by every refresh (a rotation); read only by `POST /api/auth/refresh` and `POST /api/auth/logout`, **never** on an ordinary API request.

```sql
CREATE TABLE refresh_tokens (
    id          UUID        PRIMARY KEY,
    token_hash  BYTEA       NOT NULL,    -- SHA-256 of the opaque token; never the token itself
    user_id     UUID        NOT NULL,
    family_id   UUID        NOT NULL,    -- one sign-in on one device; shared by every rotation
    expires_at  TIMESTAMPTZ NOT NULL,
    used_at     TIMESTAMPTZ NULL,        -- set when rotated; a second presentation is reuse
    revoked_at  TIMESTAMPTZ NULL,        -- set on logout or family revocation
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),

    CONSTRAINT fk_refresh_tokens_user
        FOREIGN KEY (user_id) REFERENCES users (id)
);
```

Notes:
- **Only a hash is stored.** The token is 256 random bits, base64url-encoded, handed to the client once; the table keeps its SHA-256. A leaked table therefore contains nothing that can be presented as a token. Because the input is high-entropy random data, a plain unsalted hash is sufficient — there is nothing to brute-force, and the lookup must be by exact hash.
- **This is not Google's refresh token** and not Strava's. Google tokens are never stored at all; Strava's live encrypted on `connected_sources`. This table holds only tokens **we** issued, so it needs no encryption key.
- **`family_id` groups a chain of rotations.** Login creates a new family; each `POST /api/auth/refresh` marks the presented row `used_at = now` and inserts its successor with the same `family_id`. Presenting a row whose `used_at` is already set (outside the 10–30 s grace window) revokes **every** row of the family. Logout revokes the family; "log out everywhere" revokes every family of the user.
- **`expires_at` is the 14-day idle expiry** of that one token, reset by each rotation. The **30-day absolute lifetime** of a family is measured from the family's first row; whether it is derived from the oldest `created_at` or carried on each row is specified at implementation time.
- **No `status` column.** A row is valid when `used_at IS NULL AND revoked_at IS NULL AND expires_at > now()`; the two nullable timestamps carry the "why not" as well as the "when".
- **No device or user-agent columns** in MVP. A future device list is an additive migration.
- `user_id` is a plain FK column, not a JPA association — the same persistence policy as the other IAM tables.

## Constraints and indexes

```sql
-- ---------- user_identities ----------

-- A given provider account signs in exactly one Aperitivo user.
-- Also arbitrates the first-login race (see index rationale below).
ALTER TABLE user_identities
    ADD CONSTRAINT uq_user_identities_provider_user_id_provider
    UNIQUE (provider, provider_user_id);

-- A user links a given provider at most once. Its leading column also serves
-- "which sign-in methods does this user have?" (settings page, the "cannot
-- remove the last one" guard) and the FK on user_id, so no separate
-- index on (user_id) exists.
ALTER TABLE user_identities
    ADD CONSTRAINT uq_user_identities_user_id_provider
    UNIQUE (user_id, provider);

-- ---------- connected_sources ----------

-- One identity per (provider, external id), globally. A Strava athlete
-- account can be connected to exactly one Aperitivo user at a time.
ALTER TABLE connected_sources
    ADD CONSTRAINT uq_connected_sources_provider_identity
    UNIQUE (provider, provider_user_id);

-- At most one NON-revoked source per (user, provider). Partial unique index.
CREATE UNIQUE INDEX uq_connected_sources_active_per_user_provider
    ON connected_sources (user_id, provider)
    WHERE status <> 'REVOKED';

-- Hot lookup: resolve a user's active Strava source (TokenManager, ingestion).
CREATE INDEX ix_connected_sources_user_provider
    ON connected_sources (user_id, provider);

-- Reconciliation / proactive refresh sweeps: find ACTIVE sources by expiry.
CREATE INDEX ix_connected_sources_status_expiry
    ON connected_sources (status, access_token_expires_at);

-- ---------- refresh_tokens ----------

-- The refresh lookup: one indexed read by hash. Also guarantees no two rows
-- ever share a token.
ALTER TABLE refresh_tokens
    ADD CONSTRAINT uq_refresh_tokens_token_hash
    UNIQUE (token_hash);

-- "All sessions of this user" — log out everywhere, a future device list.
CREATE INDEX ix_refresh_tokens_user
    ON refresh_tokens (user_id);

-- Family revocation on logout and on detected reuse.
CREATE INDEX ix_refresh_tokens_family
    ON refresh_tokens (family_id);

-- Cleanup job: delete rows past expires_at.
CREATE INDEX ix_refresh_tokens_expires_at
    ON refresh_tokens (expires_at);
```

Index rationale:
- `uq_user_identities_provider_user_id_provider` enforces "a sign-in method belongs to exactly one user" (invariant 3). It is also the login lookup: `findByProviderAndProviderUserId(GOOGLE, sub)` decides register-vs-login in one indexed read. `provider` leads because it is the only column meaningful on its own (`sub` is unique only within its issuer), so the index also serves per-provider queries. It is also the arbiter of the **first-login race**: when two requests for the same new `sub` both find no identity, the second `INSERT` fails with a unique violation, its whole transaction (the orphan `users` row and the `UserRegisteredEvent` publication included) rolls back, and the login is retried in a new transaction that resolves the winner's user (pattern 2 in [idempotency-and-outbox.md](../../technical-notes/idempotency-and-outbox.md); see `LoginService` in [domain-model.md](domain-model.md)).
- `uq_user_identities_user_id_provider` stops a user accumulating two Google identities. Linking a second Google account is a conflict, not an addition. Its leading `user_id` column serves lookups by user and the FK, which is why there is no separate `(user_id)` index.
- `uq_…_provider_identity` on `connected_sources` enforces invariant 2 and answers "is this Strava athlete already connected to somebody?" during the connect flow.
- `uq_…_active_per_user_provider` enforces invariant 5. Making it **partial** (`WHERE status <> 'REVOKED'`) lets a revoked row coexist with an active one for the same `(user, provider)`.
- `ix_…_user_provider` serves the hottest read — `findByUserIdAndProvider` on every token access. (It overlaps the partial unique index but is unconditional, so it also covers revoked rows for audit/history reads.)
- `ix_…_status_expiry` serves periodic sweeps: reconciliation (`findByStatus(ACTIVE)`) and any future proactive-refresh job ("ACTIVE sources expiring within the hour").
- `uq_refresh_tokens_token_hash` serves every `POST /api/auth/refresh` and `POST /api/auth/logout`: the presented token is hashed and looked up in one indexed read. At roughly one refresh per active user every 15 minutes this is the table's only hot path, and it is still trivial load ([ADR 0013](../../adr/0013-access-and-refresh-tokens.md) §6).
- `ix_refresh_tokens_family` makes "revoke the whole family" a single indexed `UPDATE … SET revoked_at = now() WHERE family_id = ?`.
- `ix_refresh_tokens_user` serves "log out everywhere" (revoke every family of the user).
- `ix_refresh_tokens_expires_at` serves the periodic job that deletes expired rows, which keeps the table from growing without bound.

### What reconnect actually does

The two `connected_sources` constraints interact, and the result decides the reconnect strategy. Spelling it out, because a plausible-sounding "just insert a new row" is wrong half the time:

| Reconnect scenario | Allowed by `uq_…_provider_identity`? | Outcome |
|---|---|---|
| Same user reconnects the **same** Strava athlete | No second row possible — `(STRAVA, athleteId)` is taken by the revoked row | **In-place reactivation**: overwrite tokens, reset `failure_count`/`last_error`, set `ACTIVE` |
| Same user connects a **different** Strava athlete | Yes, the identity differs | New row; the old revoked row stays for history (permitted by the partial index) |
| A **different** user connects that athlete | No | Rejected — `409 …/errors/source-already-linked` |

So the common case is in-place reactivation, which means **`connectedSourceId` is stable across a revoke/reconnect cycle** for the same athlete. Consumers must therefore not treat `connectedSourceId` as "a new value implies a fresh connection"; the meaningful signal is the `IntegrationConnectedEvent` itself, which fires on the transition to `ACTIVE` (see [events.md](events.md)).


## Mapping notes (entity ↔ schema)

| Entity field | Column | Mapping detail |
|---|---|---|
| `accessToken: String` | `access_token BYTEA` | `@Convert(EncryptedBytesConverter)` — AES-GCM |
| `refreshToken: String` | `refresh_token BYTEA` | `@Convert(EncryptedBytesConverter)` — AES-GCM |
| `provider: Provider` | `provider TEXT` | `@Enumerated(EnumType.STRING)` |
| `status: SourceStatus` | `status TEXT` | `@Enumerated(EnumType.STRING)` |
| `scopes: String[]` | `scopes TEXT[]` | custom `StringArrayType` |
| `version: long` | `version BIGINT` | `@Version` |
| `createdAt/updatedAt` | `created_at/updated_at` | `@CreationTimestamp` / `@UpdateTimestamp` |
| `RefreshTokenEntity.tokenHash: byte[]` | `token_hash BYTEA` | plain column; hashing happens in `RefreshTokenService`, not in a converter — the raw token never reaches the entity |

The DB `DEFAULT now()` on timestamps is a safety net; in practice Hibernate populates them via the audit annotations. `version` defaults to 0 for rows created outside the ORM (there shouldn't be any, but the default keeps optimistic locking sane).

## Migrations

- Migrations use **Flyway**, as **per-BC changesets** run at application startup. Each BC owns its own migration path; IAM's migrations live under `db/migration/identity`.
- Current IAM changeset sequence:
  1. `V1__create_schema.sql` — the `identity` schema.
  2. `V2__create_users_table.sql` — `users`.
  3. `V3__create_connected_sources_table.sql` — `connected_sources`, FK, unique constraint, indexes.
  4. `V4__create_user_identities_table.sql` — `user_identities`, FK, both unique constraints (no separate index — see above). Introduced by [ADR 0011](../../adr/0011-identity-provider-signup.md).
  5. A new changeset creates `refresh_tokens`, its FK, the unique `token_hash` constraint and the three indexes. Introduced by [ADR 0013](../../adr/0013-access-and-refresh-tokens.md); its version number is assigned when it is written.
- **Test-only migrations use versions from `V900` up** (today `V999__create_event_publication_table_for_itest.sql` under `src/test-integration/resources/db/migration/identity`). Integration tests put test resources on the same classpath location, so a test migration with a low number collides with the next production one, and Flyway refuses to start.
- `V4` is **additive only**: `users` and `connected_sources` keep their shape. Login writes only to `users` and `user_identities`, never to `connected_sources`.
- Encryption is an **application** concern: there is no DB-side crypto, and neither `user_identities` nor `refresh_tokens` stores a secret (the latter holds only hashes). A migration never needs the encryption key. This keeps key material out of the migration tool entirely.
- Adding a data-source provider later (e.g. `GARMIN`) requires **no migration** — `provider` is `TEXT`, the change is in the application `Provider` enum. The same holds for adding a sign-in provider (`APPLE`) to `user_identities`. This is the payoff of storing enums as strings.

## What is intentionally NOT here

- **No token columns on `user_identities`.** See the table notes above: an identity provider is used once per login and never called on the user's behalf afterwards.
- **No `sessions` table, and no table of access tokens.** Our access tokens are stateless JWTs validated by signature alone; we do not persist them, and there is no per-request `jti` denylist in the MVP. The only server-side token state is `refresh_tokens` above — in Postgres rather than Redis, for durability and relational queries ([ADR 0013](../../adr/0013-access-and-refresh-tokens.md) §6). There is no `HttpSession` to persist either ([ADR 0012](../../adr/0012-spa-mobile-stateless-api.md)).
- **No Google tokens anywhere.** The Google ID token is verified at login and discarded.
- **No `roles` / `authorities` table in MVP.** There is a single user type. If role-based authorization arrives later, it is an additive migration.
- **No audit-log table in MVP.** Token-access auditing is via structured logs and OTel spans (see [token-management.md](../../technical-notes/token-management.md)), not a DB table. A dedicated audit table can be added later if GDPR "what did you do with my data" reporting needs it.
- **No account-merge table.** Two accounts are never merged; there is nothing to record. See the alternatives section of [ADR 0011](../../adr/0011-identity-provider-signup.md) for why.
